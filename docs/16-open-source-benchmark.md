# 16 · 开源方案对比：libpostal、Addok、Pelias

> 不逆向别家的产品，看公开的白盒：拿最常用的三个开源地址项目，在同样的数据和评测口径下与本方案对比，找可以借鉴的地方。
> 结论先行：三个都没有比本方案好。差距主要不在"定位到哪"（差 3–5 个点），而在"能不能直接通过"：同样的准确率下，Addok 能自动通过的比例只有本方案的一半左右，Pelias 的置信度分不开对错、达不到门槛。对比中查出本方案在澳新"单元 / 门牌"写法上的一个缺陷，已修复（澳洲测试集定位对 +1.5 个点）；libpostal 作兜底只能多 1 个点左右，默认不开。

| 项目 | 是什么 | 许可 | 比什么 |
|---|---|---|---|
| [libpostal](https://github.com/openvenues/libpostal) | 全球地址解析 / 规范化（用 OSM 等数据训练的 CRF），Pelias、很多商业系统的解析层 | MIT | 只换解析：libpostal 拆出的字段送进本方案的召回和验真 |
| [Addok](https://github.com/addok/addok) | 法国国家地址 API（api-adresse.data.gouv.fr）的检索引擎，配法国国家地址库 BAN | MIT | 整条链路，巴黎：政府级地址库 + 开源检索 vs 本方案 |
| [Pelias](https://github.com/pelias) | 最常用的开源地理编码器：libpostal 解析 + Elasticsearch 检索打分 | MIT | 整条链路，悉尼 / 墨尔本：与本方案用同一份参考库，只比算法 |

评测都用开发集（各市场的真实商户地址，与 [13 文档](13-multi-market-product.md) 同一套切分），复核用测试集。脚本：[`oss_parser_eval.py`](../mvp/scripts/oss_parser_eval.py)、[`oss_geocoder_eval.py`](../mvp/scripts/oss_geocoder_eval.py)；报告：[`reports/oss_parser_eval.md`](../mvp/reports/oss_parser_eval.md)、[`reports/oss_geocoder_eval.md`](../mvp/reports/oss_geocoder_eval.md)。

## 1. libpostal：解析层

只换解析这一步，召回、验真、结论规则不变，所以差别全部来自"字段拆得对不对"。三种用法：本方案（规则 + CRF，上线配置）、只用 libpostal、本方案没直接通过时再用 libpostal 拆一次（与本地小模型的级联同一机制，参考数据裁决）。

开发集，44 个市场各 600 条真实商户地址 + 600 条合成地址：

| | 真实地址定位对 | 合成地址定位对 | 真实地址静默错误 | 真实地址直接通过且对 | 每条耗时 |
|---|---|---|---|---|---|
| 本方案 | **81.1%** | **91.7%** | 3.0% | 61.0% | 11 ms |
| 只用 libpostal | 71.8% | 74.0% | 2.2% | 52.3% | 4 ms |
| 本方案 + libpostal 兜底 | 81.3% | 91.5% | 3.0% | 61.4% | 11 ms |

- **libpostal 单独用，没有一个市场比本方案好**：欧洲、澳洲、加拿大差 0–5 个点；中东、东南亚差 10–20 个点；日本几乎不能用（真实地址 8.5%，日文地址它拆不开）；合成地址（各国写法变体）差得更多。原因是本方案的解析拿参考库当词典（道路名、片区名逐个对得上才算），libpostal 是通用模型，不认识当地的路名。
- 静默错误更低只是因为它找到的少、直接通过的少。
- **兜底用法有局部提升**：印尼 +2.5、马来西亚 +1.7、波多黎各 +1.3、墨西哥 +0.7、意大利 +0.7 个点（真实地址），但阿联酋、马来西亚、波多黎各的合成地址反而下降（阿联酋 −4.8）。
- 真实流量（0924 包里本方案 44 个市场的 573 条，不看 geo）：本方案定位对 89 条，只用 libpostal 69 条，兜底 89 条（直接通过且对多 3 条，偏差 > 500 米多 1 条）。

测试集复核（每个市场 1,000 条，开发集上兜底有提升的 5 个市场）：印尼 62.3% → 63.5%（+1.2）、墨西哥 +0.9、波多黎各 +0.9、马来西亚 +0.6、意大利 +0.1；合成地址马来西亚、波多黎各各降 1.2 个点，印尼静默错误 3.9% → 4.1%。**提升在 1 个点左右，换来的是每个进程多 2 GB 内存、启动多 10 秒和一个 C 库依赖，不值得默认开启**；印尼如果以后要再挤 1 个点，可以按市场开启。

## 2. Addok：法国国家地址 API 的做法

法国的国家地址 API 是"政府级地址库 + 开源检索"的典型做法：BAN（法国国家地址库，覆盖全国门牌）+ Addok（检索、打分）。在巴黎（含近郊 92 / 93 / 94 省）用同一批 600 条真实商户地址比，两边各用自己的数据：

| | 定位对（≤ 250 米） | 偏差 > 1 公里 | 自动通过 | 自动通过里定位对 |
|---|---|---|---|---|
| 本方案 | **94.3%** | 2.7% | **89.2%** | 97.8% |
| Addok + BAN | 89.5% | 2.8% | 46.7% | 97.9% |

- 定位能力接近（Top1 差 5 个点）：BAN 本身就是全国门牌，检索也成熟。
- **差在"能不能直接通过"**：Addok 只给 0–1 的相似度分数，没有"门牌、道路、邮编是否相互印证"的判断。要达到和本方案直接通过一样的准确率（约 98%），分数门槛只能放过 46.7%，本方案是 89.2%。这正是本方案验真层（逐字段印证 + 校准）的价值。
- Addok 1.3.2 有一个门牌匹配的缺陷（同一条结果第二次处理时报错），评测里打了补丁。

## 3. Pelias：同一份数据，只比算法

Pelias 没有用它常规的 Who's On First / OpenAddresses 数据，而是导入了本方案同一份澳洲参考库（G-NAF 门址按门牌去重后 180 万条、路网、POI，共 206 万条，带 suburb / 州 / 国家），所以两边差别全部来自算法：Pelias = libpostal 解析 + Elasticsearch 检索打分；本方案 = 规则 + CRF 解析 + 逐字段印证 + 校准。悉尼 / 墨尔本开发集 600 条真实商户地址：

| | 定位对（≤ 250 米） | 偏差 > 1 公里 | 自动通过 | 自动通过里定位对 |
|---|---|---|---|---|
| 本方案 | **86.0%** | **8.5%** | **61.8%** | 96.0% |
| Pelias | 82.7% | 12.5% | 0（达不到 96%） | — |

- 定位差 3 个点，偏差超过 1 公里多 4 个点（同名道路选错的多）。
- **Pelias 的置信度分不开对错**：526 条给了满分 1.0，其中 50 条是错的（准确率 90.5%），门槛再严也到不了本方案直接通过的 96%。它的置信度衡量的是"文字匹配得多完整"，不是"这个地址是不是真的在那里"。
- Pelias 常规部署还有门牌插值服务（interpolation），这里没有装；本方案自己有相邻门牌推算。评测脚本里 Pelias 的解析服务换成了同一个 libpostal 模型的 HTTP 替身（官方是 Go 写的 libpostal-service）。

**Pelias 对、本方案错的 24 条里查出一个本方案的缺陷**：澳洲 / 新西兰"单元 / 门牌"写法有几种没认出来——门牌是区间（`11/41-43`、`7/115-117`）、斜杠前带楼层或铺位字母（`L1/592`、`G105/1169`）、`Level 1/133-135`。原来会把单元号当门牌（`11/41-43` 查成了同一条路上的 11 号，直接通过、位置错）或丢掉门牌。已修复（[parse.py](../mvp/avmvp/intl/parse.py)），44 个市场开发集回归只有澳洲、新西兰变化，测试集同一份代码只切换这处改动：

| 测试集 | 定位对 | 直接通过且对 | 静默错误 |
|---|---|---|---|
| 澳洲 | 84.7% → **86.2%** | 73.9% → **75.7%** | 4.3% → 4.4% |
| 澳洲（合成地址） | 92.6% → **93.4%** | 85.5% → **86.3%** | 0.7% → **0.0%** |
| 新西兰 | 87.2% → **88.0%** | 68.0% → **68.9%** | 3.7% → 3.6% |

其余几条 Pelias 对、本方案错的：所写邮编那一段的门牌在官方表里根本没有（数据缺口），本方案退而选了别处同名路上的同号门牌并"替换"邮编（结论是请用户确认）。试过"邮编所指的同名路优先"的规则，这几条都触发不了（缺的是那一段的门牌），所以没有改。

## 4. 借鉴什么、不借鉴什么

**结论：三个开源项目都没有比本方案好**，可借鉴的已经吸收：

| | 可借鉴 | 处理 |
|---|---|---|
| libpostal | 通用解析能力（没见过的写法也能拆） | 只在印尼等少数市场作兜底能多 1 个点左右，不值 2 GB 内存，默认不开 |
| Addok + BAN | "全国门牌库 + 轻量检索"就能把定位做到接近本方案（差 5 个点） | 印证了"数据覆盖"才是主要杠杆（与 [00 文档第 6 节](00-final-mvp-solution.md) 的失败分桶一致）：法国这种国家级门牌库开放的市场，全国扩展的成本很低 |
| Pelias | 解析写法覆盖（单元 / 门牌区间等） | 对比中查出澳新的单元写法缺陷，已修复：澳洲测试集 +1.5、新西兰 +0.8 |

**不借鉴的：开源引擎都只有"文字匹配得多像"的分数，没有"门牌、道路、邮编、片区相互印证"的判断，也没有按真实正确率校准。** 这正是同样准确率下，本方案能直接通过的比例是 Addok 的约 2 倍、Pelias 的分数根本达不到门槛的原因，也是本方案对标 Google AV 的核心。

**复现**：libpostal 从源码编译（模型数据 1.9 GB）；Addok 装在单独的虚拟环境，配 Redis，导入 BAN 的 addok 格式导出；Pelias 用 Elasticsearch 7.17（需要非 root 用户运行，装 analysis-icu 插件）+ pelias/schema、csv-importer、api。命令见两个脚本的文件头。
