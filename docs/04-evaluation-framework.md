# 04 · 评测体系：怎么证明我们比 Google 好（或差多少）

> 原则：**先有尺子，再造东西。** 在写第一行 AV 代码之前，先建 Golden Set、定义指标、拿到 Google 和现有 Geocoder 的 baseline。所有产品决策、版本发布、对外宣传都以这套评测为准。

---

## 1. 两套评测集

| 评测集 | 构成 | 用途 |
|---|---|---|
| **自然分布集** | 从真实业务流量（客户下单地址、搜索日志）中随机抽样 | 反映**真实世界**的表现，用来估算上线后的业务影响 |
| **压力测试集** | 按错误类型**分层**构造 / 抽样 | 定位**具体短板**，每一类都有足够样本量 |

> 只看自然分布集，稀有但关键的错误类型（如"不存在的门牌"）样本太少、看不出问题；只看压力测试集，会高估错误出现的频率。**两套都要。**

---

## 2. 压力测试集的 9 类样本

| 类别 | 说明 | 示例（新加坡，示意） | 期望动作 |
|---|---|---|---|
| A 标准正确 | 完整、正确、格式规范 | `10 Bayfront Avenue, Singapore 018956` | ACCEPT |
| B 格式混乱 | 信息完整但顺序颠倒、缩写、大小写、多语混写 | `018956 10 bayfront ave s'pore` | ACCEPT（或仅格式化后 CONFIRM） |
| C 拼写错误 | 可唯一纠正的拼写错误 | `10 Bayfrnt Avenue 018956` | CONFIRM |
| D 缺组件 | 缺邮编 / 缺门牌 / 缺城市 | `1 Raffles Place`（缺邮编，可推断） | CONFIRM（可推断）或 FIX（不可推断） |
| E 组件冲突 | 组件之间互相矛盾 | `10 Bayfront Avenue, Singapore 819643`（邮编属于别处） | CONFIRM（可唯一修正）或 FIX |
| F 不存在 | 虚构的门牌 / 楼号 / 单元 | `999 Bayfront Avenue 018956` | FIX |
| G 非正式地址 | 地标 / POI 描述、无门牌 | `Changi Airport Terminal 3` | 视规则包而定 |
| H 旧地址 | 旧街道名、旧行政区划（越南尤其重要） | —（越南样本） | CONFIRM（输出新标准地址） |
| I 单元级 | 带单元号，含正确 / 错误 / 缺失三种 | `Blk 123 … #05-12` / `#25-12`（超出最高层） / 缺单元 | ACCEPT / FIX / CONFIRM_ADD_SUBPREMISES |

模板见 [`templates/golden-set-template.csv`](../templates/golden-set-template.csv)。

### 样本量怎么定

以"误收率约 2%，希望估计误差 ±1%（95% 置信）"为例：
`n ≈ 1.96² × 0.02 × 0.98 / 0.01² ≈ 750` 条**坏地址**。
**建议起步：每个国家 3,000–5,000 条，每个关键类别 ≥ 300 条；MVP 阶段新加坡先做 500 条 v0，再逐步扩充。**

## 3. 真值标注

每条样本需要标注：

| 字段 | 说明 |
|---|---|
| `expected_is_real` | 用户想表达的地址是否真实存在且可唯一确定 |
| `expected_action` | 期望动作（ACCEPT / CONFIRM / FIX / CONFIRM_ADD_SUBPREMISES） |
| `expected_standardized_address` | 正确的标准地址（若存在） |
| 各组件真值 | 门牌、单元、街道、邮编…… |
| `expected_lat/lng` | 楼栋点，若可得再加入口点 |
| `label_source` | 真值来源：权威数据 / 投递成功记录 / 实地核验 / 人工标注 |

**标注流程建议：**

1. 优先用**投递成功记录**和**权威数据**自动生成真值（最可靠、成本最低）
2. 其余样本**双人独立标注**，不一致由第三人仲裁；记录一致率（Cohen's κ），κ 过低说明标注规范有问题
3. 抽 3–5% 做**实地核验**或电话核验，校准整体标注质量
4. 标注规范文档化，特别是 G 类（非正式地址）"算不算完整"的判定标准

---

## 4. 指标定义

### 4.1 结论层（最重要，直接对应业务损失）

把 4 种动作排成 4×4 **混淆矩阵**（行 = 期望动作，列 = 系统动作），并重点看三个派生指标：

| 指标 | 定义 | 业务含义 |
|---|---|---|
| **误收率 FAR** | 期望为 FIX / ADD_SUBPREMISES 的样本中，系统输出 ACCEPT 的比例 | 坏地址被放过 → 退件、改派、客诉 |
| **误拒率 FRR** | 期望为 ACCEPT 的样本中，系统输出 FIX 的比例 | 好地址被拦 → 结账流失、用户挫败 |
| **过度打扰率 UCR** | 期望为 ACCEPT 的样本中，系统输出 CONFIRM 的比例 | 多一步确认 → 轻度流失 |

**把它换算成钱**（给管理层和客户看）：

```
每千单期望损失 = 1000 × [ P(坏地址) × FAR × C_误收
                        + P(好地址) × FRR × C_误拒
                        + P(好地址) × UCR × C_打扰 ]
```

`C_误收`（一次退件 / 改派成本）、`C_误拒`（一次流失订单的利润）、`C_打扰`（一次额外确认的流失概率 × 利润）需要和客户一起估算。**不同客户算出来的最优严格度档位不同——这正是提供档位配置的依据。**

### 4.2 修正层

| 指标 | 定义 |
|---|---|
| **修正准确率** | 系统做了修正 / 补全 / 替换的样本中，修正后地址与真值一致的比例（**目标应非常高**，错误修正比不修正更糟） |
| **修正召回率** | 可唯一修正的样本中，系统给出正确修正的比例 |

### 4.3 组件层

对每种组件类型（门牌、单元、街道、邮编、区……）：

- **错误检出率**：真值为错误的组件中，被标为 `UNCONFIRMED_AND_SUSPICIOUS` 或 `replaced` 的比例
- **误伤率**：真值为正确的组件中，被标为 `UNCONFIRMED_AND_SUSPICIOUS` 的比例

### 4.4 标准化层

- **标准地址完全一致率**：规范化比较（大小写、空白、缩写统一）后与真值标准地址完全一致的比例
- **字段级一致率**：逐字段一致的比例

### 4.5 覆盖与定位层

| 指标 | 定义 |
|---|---|
| **PREMISE 覆盖率** | 真实地址中，验证粒度达到 `PREMISE` 及以上的比例（按区域出热力图） |
| **SUB_PREMISE 覆盖率** | 带单元号的真实地址中，单元级得到确认的比例 |
| **定位误差** | 与真值点的距离 P50 / P90；≤ 30m 命中率 |

### 4.6 性能与成本层

延迟 P50 / P95 / P99、错误率、可用性、每千次调用的成本（含数据授权分摊）。

## 5. 与 Google 的对比测试（Side-by-side）

1. 同一套 Golden Set，同时跑三条线：**Google AV**、**现有 Geocoder（映射为动作）**、**我们的 AV 各版本**
2. 现有 Geocoder 的动作映射示例：屋顶级匹配且得分高 → ACCEPT；插值 / 街道级 → CONFIRM；其他 → FIX。这是"什么都不做"的 baseline，用来量化 AV 的增量价值
3. Google 的 `possibleNextAction` 直接对应 4 类动作
4. 输出报表：**国家 × 类别 × 指标 × 系统**

示意报表：

| 国家 | 类别 | 指标 | Google AV | 现有 Geocoder | 我们 v0.1 |
|---|---|---|---|---|---|
| SG | 全部 | FAR | | | |
| SG | 全部 | FRR | | | |
| SG | F 不存在 | FIX 检出率 | | | |
| SG | I 单元级 | 缺单元检出率 | | | |
| VN | H 旧地址 | 修正准确率 | 不覆盖 | | |

> ⚠️ **法务提醒（重要）：** Google Maps Platform 服务条款限制对其内容的存储、缓存，以及利用其内容创建或改进竞品。对比测试请在法务指导下进行，建议：
> - 仅保留聚合指标，不留存 Google 的原始响应
> - **绝不**把 Google 的输出用作训练数据、标注真值或参考库数据来源
> - 真值必须来自独立来源（权威数据、投递记录、人工 / 实地核验）

## 6. 发布门槛与持续评测

**MVP（新加坡）建议初始目标**——请在拿到 baseline 后校准：

| 指标 | 建议目标 |
|---|---|
| FAR（Balanced 档位） | ≤ 2%，且不劣于 Google |
| FRR（Balanced 档位） | ≤ 3%，且不劣于 Google |
| 修正准确率 | ≥ 97% |
| PREMISE 覆盖率 | ≥ 97% |
| HDB 缺单元号检出率 | ≥ 90%（Google 在美国以外基本不具备） |
| 延迟 | P95 ≤ 200ms |

**持续评测机制：**

- 每次发布（参考库、规则包、模型任一变更）跑全量 Golden Set；关键指标回退超阈值则**阻断发布**
- 每月从线上流量补充新样本，防止评测集"过时"
- 线上监控：各国结论分布、客户反馈中"采用修正版本"的比例、设计伙伴的**投递失败率变化**（最终的业务北极星指标）
