# 13 · 多市场地址校验：成品说明（45 个市场）

> 目标：一套服务覆盖 **Google Address Validation 覆盖的全部国家 / 地区（美国除外）**，外加中东和东南亚，共 45 个市场；接口对齐 Google AV；每个市场用同一套方法评测"规则 / AI / 规则 + AI"。
> 代码：[`avmvp/intl/`](../mvp/avmvp/intl)（多市场引擎）、[`avmvp/router.py`](../mvp/avmvp/router.py)（按国家分发）、[`avmvp/server.py`](../mvp/avmvp/server.py)（HTTP 服务 + 演示页面）
> 报告：[与 Google 对标（测试集）](../mvp/reports/google_parity.md)、[多市场评测（测试集）](../mvp/reports/markets_eval.md)、[置信度校准](../mvp/reports/intl_confidence_report.md)、[直接通过放宽规则](../mvp/reports/accept_policy.md)、[AI 解析器训练](../mvp/reports/crf_training.md)

## 1. 结论

| 问题 | 回答 |
|---|---|
| 覆盖了哪些市场？ | **45 个**：Google AV 覆盖的 40 个国家 / 地区里除美国外的 39 个（38 个已正式上线、日本和印度 2 个预览，见 [01 文档](01-google-av-teardown.md)），外加 Google 没有覆盖的阿联酋、沙特、印尼、泰国、越南、菲律宾。新加坡用专用引擎，其余 44 个用多市场引擎，每个国家一个试点城市（澳洲两个） |
| 能验到什么粒度？ | **29 个 A 类市场有开放官方地址表，逐门牌验真**：澳洲、新西兰、日本、加拿大、墨西哥、巴西、智利、哥伦比亚，以及欧洲 21 国（德、法、荷、比、卢、瑞士、奥地利、意、西、葡、丹麦、挪威、芬兰、爱沙尼亚、拉脱维亚、立陶宛、波兰、捷克、斯洛伐克、斯洛文尼亚、克罗地亚）；新加坡另算。**15 个 B / C 类市场没有开放地址表**（中东 2 国、东南亚 5 国、英国、爱尔兰、瑞典、匈牙利、保加利亚、阿根廷、印度、波多黎各），验到道路 / 楼宇 / 片区 |
| 效果怎么样？ | 真实商户自填地址（每市场 1,000 条测试样本，商户本身不在参考库里）：**A 类找对的中位数 86%（56–96%），直接通过的中位数 78%**；欧洲 B / C 类（匈牙利、瑞典、英国、保加利亚）82–94%；中东 33–37%、东南亚 60–72%、印度 35%。**偏差超过 1 公里的静默错误：42 个市场 ≤ 2.3%**，斯洛文尼亚（6.1%）、拉脱维亚（4.0%）偏高，核对过主要是商户坐标本身标错（第 2 节） |
| 规则好还是 AI 好？ | **混合最好**：规则和机器学习都出候选、由参考数据裁决，在 **44 个市场的真实地址上全部是最好或并列最好**。纯机器学习在合成地址上常常最好，在真实地址上最差。本地小模型（Qwen）兜底只多 0–4 个百分点、每次 7–9 秒，默认关闭（第 6 节） |
| 怎么保证不乱放行？ | 每条"直接通过"的规则都在开发集上校准过：默认规则来自东南亚的统计（第 7 节），**另按市场、按证据组合在开发集上统计，足够可靠的组合才放宽**（目前 3 条：英国、立陶宛、保加利亚）。每个结论带**校准过的置信度**：44 个市场测试集上校准误差 **1.1%**，区分对错的 AUROC **0.891**。客户可以用 `confidenceThreshold` 自己设门槛 |
| 瓶颈在哪？ | A 类：官方地址表本身的完整度（葡萄牙、墨西哥、哥伦比亚的地址表只覆盖部分门牌，日本只到街区）。B / C 类：参考数据，不是解析，合成地址能到 76–99%，真实地址差距来自只写楼名 / 商户名、同名道路。**接入自有楼栋 / 门牌数据，同一引擎就走 A 类的逐门牌路径** |
| 新加坡 | 专用引擎（[07](07-mvp-technical-validation.md)、[11](11-research-testset.md)）：真实人写地址直接通过 85.9%，误拒 0.7%，静默错误 0 |

- **"偏差 >1 公里"偏高的几个 A 类市场**：斯洛文尼亚 6.1%、拉脱维亚 4.0%、新西兰 2.3%、卢森堡 2.2%。开发集上逐条核对过斯洛文尼亚和日本的这类样本：道路、门牌与官方地址点完全一致，地址点位置也对，**是商户坐标本身标在了几公里外**（POI 平台把商户放在了别处）。所以这些市场的数字是弱标注噪声的上限，不是引擎错误率；上线后要用真实订单的签收坐标重新统计（第 9 节）。
- **A 类"判 FIX"**：门牌不在官方表里、或没写门牌（葡萄牙 32%、墨西哥 25%、哥伦比亚 21%）。葡萄牙、墨西哥、哥伦比亚的地址表只覆盖部分门牌；紧挨着的门牌在表里时，引擎按相邻门牌给出位置并要求确认（`PREMISE_INTERPOLATED`，第 3.2 节），不再一律判 FIX。
- **B / C 类"错误建议"比例高**（东南亚 19–30%、中东 35–43%）：同名道路多、只能验到道路，这些都**要求用户确认并给出候选**，不计入静默错误。欧洲的 C 类市场这一项只有 3–6%（英国、瑞典、匈牙利、保加利亚），邮编精确、路名少重复，道路级结论本身就可靠。

**评测切分**：开发集是每个市场打乱后的第 600–1199 条真实地址，测试集从第 1200 条起，两者固定、永不重叠。上面的数字是在开发阶段从未看过的测试集上跑的，跑完之后没有再改代码。最初 11 个市场按新代码重建了参考库并重新评测：A 类定位对的比例上升 1–4 个百分点（相邻门牌推算），B / C 类变化在 ±1 个百分点以内，开发集上逐项对比没有退步。

## 3. 产品形态

### 3.1 接口

```bash
python -m avmvp.server            # http://127.0.0.1:8080/  演示页面（可选 45 个市场）
```

| 接口 | 说明 |
|---|---|
| `POST /v1/address:validate` | 请求体与 Google AV 相同：`{"address": {"regionCode": "JP", "addressLines": ["…"], "locality": "…", "postalCode": "…"}, "strictness": "BALANCED"}`；`regionCode` 用 ISO 国家代码（英国写 GB），决定用哪个市场的引擎，缺省为 SG |
| `POST /v1/address:batchValidate` | 批量：`{"requests": [与单条相同的请求体, …]}`，最多 1,000 条，单条出错只影响该条（Google AV 没有原生批量接口，Loqate 有） |
| `GET /v1/markets` | 开放的市场、类别（A / B / C）、覆盖城市、参考数据是否已构建 / 已加载 |
| `GET /healthz` | 健康检查 |

完整接口说明见 [openapi.yaml](openapi.yaml)（OpenAPI 3，可直接导入 Postman / Swagger 生成调用代码）。

**离线批量清洗**（主数据清洗、历史订单回扫）：`python scripts/batch_validate.py input.csv output.csv --region-column country --column address`，在原表后追加结论、粒度、标准化地址、坐标、原因码和候选。

**部署**：[`mvp/Dockerfile`](../mvp/Dockerfile)。参考数据不打进镜像、运行时挂载（`docker run -p 8080:8080 -v $PWD/data:/app/data address-validation`），数据更新不用重新发版；各市场的参考库在第一次请求时加载（44 个市场合计约 3.8 GB，最大的澳洲约 650 MB）。

响应字段与新加坡引擎一致（`verdict.possibleNextAction / validationGranularity / reasons / confidence`、`address.formattedAddress / addressComponents / missingComponentTypes`、`geocode.location / plusCode`、`nonAddressInfo`、`candidates`），多市场引擎另有 `result.codes`（Plus Code、迪拜 Makani、沙特国家地址短码）和 `result.metadata`（`regionCode`、`marketClass`、`parser`）。标准化地址按当地习惯排版：`Vodičkova 1935/38, 110 00 Praha`、`Carrera 14 # 66-33`、`〒150-0041 渋谷区神南一丁目12`、`20 Camden St, Toronto ON M5V 1V1`。

### 3.2 结论怎么定

| | A 类（29 个市场 + 新加坡） | B 类（中东）/ C 类（没有开放地址表） |
|---|---|---|
| 验真依据 | 官方地址表：这条路上有没有这个门牌；官方表没有时再看 OSM 门牌、商户地址门牌点 | 地图数据（道路、片区、邮编、楼宇 / POI）+ **OSM 门牌**、商户地址门牌点 |
| 最高粒度 | `PREMISE`（门牌），多单元楼缺单元号时 `CONFIRM_ADD_SUBPREMISES` | `PREMISE`（OSM 门牌）、`PREMISE_PROXIMITY`（推算 / 商户门牌点 / 楼宇 / Plus Code）、`ROUTE`（道路） |
| ACCEPT | 门牌在官方表里，且没有纠错 / 替换；只有 OSM 有的门牌按开发集校准的组合放行 | 门牌点 / 道路级：邮编与道路相互印证、道路名在城市里唯一、名称完全一致（或该市场开发集上校准过的同样可靠的组合，第 7 节）；楼宇在所写道路旁；Plus Code / 坐标与所写道路、片区一致 |
| CONFIRM | 道路名纠错、邮编被替换、只凭楼宇定位、门牌按相邻门牌推算（`PREMISE_INTERPOLATED`）、门牌来自商户登记（`PREMISE_FROM_POI`）；**道路对上、门牌不在表里**（`ROUTE` + `PREMISE_NOT_FOUND`，与 Google 一致） | 缺少印证或同名道路不止一条、只匹配上部分道路名、拼写纠错、缺门牌 / 楼名 |
| FIX | 没写门牌，或只能确认到片区 / 什么都找不到 | 只能确认到片区，或什么都找不到 |

门牌位置的来源依次是：官方地址点 → OSM 门牌点（`PREMISE_FROM_OSM`）→ 商户地址门牌点（参考库里商户自填地址解析出的"道路 + 门牌"，`PREMISE_FROM_POI`）→ 推算（`PREMISE_INTERPOLATED`）：同一条路上 ±2、±4、±6（同侧优先），再试 ±1、±3、±5，再按上下两个同侧门牌的号码比例插值；哥伦比亚按"交叉街编号"找同一街区（`# 31-10` → 31-08 / 31-24），只写了交叉街编号时取街区中间的门牌；日本街区号不按位置排列，不推算。推算位置离所写邮编太远的不用。

### 3.3 处理流程

```
输入 ─► 噪声剥离（电话 / 邮箱 / 网址）+ 编码识别（Plus Code / Makani / 沙特短码）
     ─► 统一写法：去重音、西里尔文转写、日文町丁目统一、各国缩写展开、邮编规范化
     ─► 解析（两者都出候选）：规则 + 地名表 │ 机器学习（CRF）
     ─► 召回：道路（完整名 / 去类型词 / 容错 / 阿拉伯文转写 / 泰文无空格 / 日文罗马字别名）、片区、楼宇 / POI、邮编（含上一级片区）
     ─► 证据打分：官方地址点、相邻门牌、片区包含、邮编距离、楼宇距离、同名道路消歧
     ─► 结论 + 粒度 + 坐标 + 逐组件确认级别 + 原因码 + 置信度
```

各市场的写法差异放在配置里（[`markets.py`](../mvp/avmvp/intl/markets.py)、[`text.py`](../mvp/avmvp/intl/text.py)），引擎不分国家写逻辑：

| 写法差异 | 例子 |
|---|---|
| 门牌在道路前 / 后 | `12 Smith St`（英语国家、法国、卢森堡）/ `Musterstraße 12`（其余欧洲、拉美）|

## 5. 评测方法

| 测试集 | 做法 | 标准答案 | 判对标准 |
|---|---|---|---|
| **真实商户地址**（每市场 1,000 条） | 留出的 20% 商户在 Meta / Foursquare / 微软等平台自填的地址 + 城市 + 邮编，和结账表单一样 | 商户坐标（弱标注） | 门牌级 ≤ 250 米、楼宇级 ≤ 400 米、道路级为该道路经过商户 250 米内、片区级 ≤ 3 公里 |
| **合成地址**（每市场 1,000 条） | 按各市场写法渲染"测试部分"的道路（按道路名哈希分，AI 解析器训练时没见过这些道路名），30% 加拼写 / 大小写噪声 | 渲染时用的道路 / 地址点 | 找对道路（A 类找对地址点：同一门牌在地址表里有多个点时，门牌一致即可） |

- **开发集和测试集分开**：开发集（每市场 600 条真实 + 600 条合成）用于迭代、校准放宽规则和拟合置信度，测试集只在最后运行。
- **弱标注的误差**：商户坐标本身不总是准的，而且各国差别很大（斯洛文尼亚、拉脱维亚明显偏高，见第 2 节）。所以另外统计**"偏差 >1 公里"的静默错误**，并在开发集上逐条核对过偏高市场的样本。
- **结果分类**：正确·直接通过 / 正确·要求确认 / 判 FIX / 错误建议（给错但要求确认，用户有机会发现） / **静默错误**（给错且直接通过，最危险）。

## 6. 规则和 AI：数据给出的回答

三种解析方式都用同一个参考库和同一套证据打分，只有"理解输入"这一步不同：
- **规则**：地名表最长匹配 + 各市场写法规则。

1. **在真实地址上，混合方案在全部 44 个市场都是最好或并列最好**（与最初 11 个市场的结论一致）。纯机器学习在合成地址上常常最好，在真实地址上反而最差：它只见过按模板渲染的地址，真实写法（楼名在前、夹杂商户名、邮编写两遍、Plus Code）比模板多样得多。**机器学习的价值是补规则的漏，不是替代规则。**

   - **提升 0–4 个百分点，且因市场而异**：菲律宾、阿联酋、沙特在开发集和测试集上都是正的；**泰国两次都是负的**（模型对泰文拆出的候选排在了原本正确的结果前面）。4B 模型略好于 1.5B。两个模型都**没有增加静默错误**（上面的"最多 CONFIRM"规则起了作用：不加这条时，阿联酋、沙特开发集上模型带来的直接通过里出现了偏差 >1 公里的错误）。
   - **代价**：中东、东南亚 60–97% 的请求都会触发模型，CPU 上每次 6–10 秒。结账页实时校验用不了；批量清洗可以，或者上 GPU（4B 模型在一张推理卡上约零点几秒一次）。
   - **模型读对、规则漏掉的，主要是可以写成规则的写法**：菲律宾"路名 门牌"不写 St（`Kapiligan 84`）。改写成规则后，菲律宾开发集 +2 个百分点，和模型带来的提升相当，成本几乎为零（第 8 节）。
   - **结论**：与新加坡一致（[08 文档](08-ai-local-model.md)）：AI 适合做"发现规则漏掉的写法"的工具和可选兜底，不是主路径。中东、东南亚真正的瓶颈是参考数据（只写楼名 / 商户名、同名道路），模型读得再懂也补不上库里没有的楼。服务里用 `--intl-llm <GGUF 文件或接口地址>` 开启，`--intl-llm-markets` 指定市场，默认只在开发集上有提升的菲律宾、阿联酋、沙特开启（测试集结果与开发集一致）。

## 7. 结论规则是怎么定的（开发集校准）

### 7.1 默认规则

B / C 类没有门牌数据，**"道路级直接通过"是最容易出静默错误的地方**。在开发集上按证据组合统计了道路级 ACCEPT 的准确率（7 个市场，1,320 条）：

| 证据组合 | 条数 | 道路经过商户 250 米内 | 偏差 >1 公里 |
|---|---|---|---|
| 邮编 + 片区印证，名称完全一致，道路名唯一 | 378 | 88.6% | 3.4% |
| 邮编印证，名称完全一致，道路名唯一 | 231 | 88.7% | 3.9% |
| 邮编 + 片区印证，名称去类型词一致，道路名唯一 | 55 | 83.6% | 0.0% |
| 邮编 + 片区印证，但同名道路不止一条 | 149 | 84.6% | 7.4% |
| 只有片区印证，道路名唯一 | 102 | 85.3% | 9.8% |
| 没有任何印证，道路名唯一 | 152 | 78.9% | 15.8% |
| 只有片区印证，同名道路不止一条 | 37 | 59.5% | 37.8% |

于是规定：**道路级直接通过需要"邮编与道路相互印证 + 道路名在试点城市唯一 +（名称完全一致或片区也印证）"**，否则要求确认（原因码 `ROUTE_NOT_CORROBORATED`）。调整后 B / C 类"偏差 >1 公里的静默错误"从 2.5–4% 降到 0.2–1.5%，接近约 1% 的标注噪声下限；代价是直接通过率下降。阿联酋没有邮编，道路级一律要求确认，直接通过只来自楼宇（楼名在所写道路旁）和 Plus Code。

### 7.2 按市场放宽（开发集校准）

默认规则来自东南亚的统计。新增的国家里，有的证据组合在本市场明显更可靠，比如保加利亚多数地址不写 `ul.`，道路名靠"去类型词"对上，默认规则要求名称完全一致。所以对每个市场、每种证据组合，在开发集上单独统计，**样本 ≥ 25、正确率 ≥ 95%（Wilson 下界 ≥ 88%）、偏差超过 1 公里 ≤ 2%** 的组合才允许直接通过（[`scripts/fit_accept_policy.py`](../mvp/scripts/fit_accept_policy.py)，结果存 `models/accept_policy.json`）：

| 市场 | 放宽的组合 | 开发集样本 | 正确 | 偏差 >1 公里 |
|---|---|---|---|---|
| 英国（GB） | OSM 门牌点：邮编印证 + 名称完全一致（同名道路不止一条也行） | 117 | 99.1% | 0.9% |
| 英国（GB） | 道路级：邮编印证 + 名称完全一致，同名道路不止一条 | 204 | 98.5% | 1.0% |
| 瑞典（SE） | OSM 门牌点：邮编印证 + 道路名唯一 + 名称完全一致 | 360 | 96.4% | 1.4% |
| 瑞典（SE） | 道路级：邮编印证 + 名称完全一致，同名道路不止一条 | 50 | 98.0% | 2.0% |
| 匈牙利（HU） | OSM 门牌点：邮编印证 + 道路名唯一 + 名称完全一致 | 245 | 96.3% | 1.6% |
| 保加利亚（BG） | OSM 门牌点：邮编印证 + 道路名唯一 + 去类型词后一致（多数地址不写 ul.） | 174 | 97.1% | 0.6% |
| 加拿大（CA） | 官方表没有、只有 OSM 有的门牌：邮编印证 + 道路名唯一 + 名称完全一致 | 102 | 97.1% | 2.0% |
| 阿根廷（AR） | 道路级：邮编 + 片区印证 + 名称完全一致，同名道路不止一条 | 207 | 95.2% | 1.9% |
| 立陶宛（LT） | 门牌由官方地址点确认，只有邮编被替换（邮编细到路段，商户常写邻段的） | 102 | 100.0% | 0.0% |
| 巴西（BR） | 门牌由官方地址点确认，只有邮编被替换 | 110 | 95.5% | 0.9% |

没有官方表的市场，OSM / 商户门牌点没被放宽时按道路级规则决定，这些样本也计入对应的道路级组合。接近但没达标的组合（爱尔兰 OSM 门牌点 83%、马来西亚 85%、英国"OSM 门牌点 + 邮编印证 + 道路名唯一"96.1% 但偏差 >1 公里 2.4%）仍按默认规则。完整统计见 [reports/accept_policy.md](../mvp/reports/accept_policy.md)。

### 7.3 置信度：给客户一个可以自己调的门槛

和新加坡（[09 文档](09-bayesian-scoring.md)）同一做法：**置信度 = 同一类结论在开发集真实地址上"位置给对"的实际比例**。类别由证据组成（市场、结论、粒度、哪些字段相互印证、道路名是否唯一、关键原因码），样本少的细类向粗类收缩。接口响应里带 `verdict.confidence` 和一句解释（`confidenceNote`："开发集上同类结论 N 条中位置给对了 M 条"）。Google AV 不提供这个字段。

**测试集检验**（44 个市场、43,425 条给出位置的结论，开发阶段未看过；[完整报告](../mvp/reports/intl_confidence_report.md)）：期望校准误差 **1.1%**，区分对错的 AUROC **0.891**。

| 置信度区间 | 条数 | 平均置信度 | 实际给对 |
|---|---|---|---|
| 0.00–0.50 | 5,351 | 19.6% | 16.7% |
| 0.50–0.70 | 2,396 | 60.0% | 56.2% |
| 0.70–0.80 | 2,028 | 75.6% | 73.2% |
| 0.80–0.90 | 5,182 | 86.3% | 86.3% |
| 0.90–0.95 | 7,905 | 93.3% | 92.8% |
| 0.95–1.00 | 20,563 | 97.3% | 96.7% |

**按门槛自动通过**（请求里传 `confidenceThreshold`，低于门槛的 ACCEPT 改为 CONFIRM）：

| 类别 | 门槛 | 自动通过占全部 | 自动通过里的错误率（严格） | 其中偏差 >1 公里 |
|---|---|---|---|---|
| A | 不设 | 74.3% | 4.0% | 1.8% |
| A | ≥ 0.90 | 71.4% | 3.8% | 1.7% |
| A | ≥ 0.95 | 57.0% | 3.2% | 1.2% |
| B | 不设 | 3.0% | 23.3% | 16.7% |
| B | ≥ 0.90 | 1.0% | 30.0% | 15.0% |
| C | 不设 | 38.3% | 6.0% | 2.7% |
| C | ≥ 0.90 | 31.1% | 4.5% | 2.1% |
| C | ≥ 0.95 | 21.8% | 3.1% | 1.5% |

**怎么用**：
- **A 类**：不设门槛时自动通过 74%，偏差 >1 公里 1.8%（含斯洛文尼亚、拉脱维亚的坐标噪声）；要更稳可以设 0.95，自动通过降到 57%、偏差 >1 公里降到 1.2%。
- **C 类**：建议设 0.9，自动通过 31%，其中偏差 >1 公里 2.1%。欧洲的 C 类市场（英国、瑞典、匈牙利）置信度普遍在 0.9 以上，东南亚多在 0.9 以下，门槛自然按市场起作用。
- **B 类（中东）**：不做自动通过，全部走"要求确认 + 候选"，直到接入自有楼栋数据。

| 菲律宾、马来西亚 | `2F`、`GF` 楼层当门牌；`Sto. Tomas` 的 Sto 没展开 | 楼层写法识别；`Sto / Sta / Gen / Brgy / Ext` 展开 |
| 菲律宾 | `Kapiligan 84, Quezon City`（路名 + 门牌、不写 St）认不出道路。**这是本地小模型读对、规则漏掉的主要写法**（见第 6 节） | 段首名称紧跟门牌号时允许省略类型词：开发集真实地址 +2 个百分点，与小模型带来的提升相当，成本几乎为零 |
| 阿联酋 | 邮编栏填的是邮政信箱号（`5280 DUBAI`），被当门牌 | 除首段外只有数字的一段视为信箱号，单独抽出；`Villa 12` 视为门牌 |
| 沙特、阿联酋 | 英文写法（`Ibn Taymiyyah St.`）找不到只有阿拉伯文名称的道路 | **转写骨架**：两边都只比较辅音（ث/ت → T、ق/ك → K …），`Ibn Taymiyyah` 与 `ابن تيمية` 都是 `BNTM` |
| 沙特、阿联酋 | Plus Code（`PRX9+WV5`）只识别不定位；`00000` 占位邮编被当成矛盾 | **Plus Code 解码**（按公开规范实现，含短码按城市补齐），与所写道路 / 片区核对；占位邮编忽略 |
| 越南 | 5 位新邮编（71106）没识别，被当门牌 | 邮编 5 位 / 6 位都认 |
| 全部 | 长路只有路段中点，定位和距离都偏 | 路段带线形下载，沿线约 80 米取点；同名路段按线形合并 |
| 印尼、马来西亚、菲律宾 | `Jalan M H Thamrin` 在参考库里叫 `Jalan Mohammad Husni Thamrin`，匹配到 14 公里外另一条 `MH Thamrin` | 构建参考库时给人名道路生成缩写别名（`Mohammad Husni` → `MH`、`Kyai Haji` → `KH`）：印尼开发集 +3.5 个百分点 |
| 阿联酋 | `Mall of Emirates` 里的 Emirates 被当成 13 公里外的 Emirates Street；`Behind Mall of Emirates`（在商场后面）被当成商场本身；`FMC Medical Center` 纠错成 `NMC Medical Center` 后直接通过 | 带楼宇词的片段优先找楼名；参照物描述（behind / opposite / near、خلف / مقابل）和纠错得到的楼名不直接通过；`Building 9` 这类通用楼名不作证据：阿联酋开发集偏差 >1 公里的静默错误 1.2% → 0.3% |
| 沙特、阿联酋 | `Prince Ahmad Bin Abdulaziz St` 只匹配上 "Ahmad" 一个词 | 只匹配上单个词时让位给更长的转写匹配 |
| 全部 | 英文输入返回马拉雅拉姆文地名（`ദുബായ് മറീന`） | 拉丁字母判断改用精确的 Unicode 区段 |
| 荷兰、澳洲 | `35hs`、`162A`、`283-30`（荷兰：门牌 + 附加）、`51-55 Memorial Ave`（澳洲：门牌区间）查不到 | 荷兰附加号码记为单元；区间按首尾门牌查。**这一条是在测试集错误分析里发现的**（开发集里同样常见），见第 2 节说明 |

## 9. 局限与下一步

| 局限 | 影响 | 下一步 |
|---|---|---|
| 每个国家只建了一个试点城市 | 结果代表首都 / 最大城市，乡村写法（巴西、墨西哥的农村地址）没覆盖 | `markets.py` 里扩大范围后重跑 `fetch_markets.py` / `build_market_reference.py`，引擎不用改 |
| 部分地址表标为专有许可 | 澳洲、巴西、加拿大、墨西哥、丹麦、爱沙尼亚、克罗地亚、瑞士 | 法务逐一确认；或与当地机构签约获取授权数据 |
| 地址表不完整 / 只到街区 | 葡萄牙、墨西哥、哥伦比亚判 FIX 21–32%；日本只到街区（约 50–100 米） | 换官方全量数据（CTT、INEGI、Catastro Bogotá、日本住所基礎番号）；没有门牌时已按相邻门牌给位置 |
| B / C 类没有门牌数据 | 中东直接通过 2–3%、东南亚 11–33%、印度 12% | **接入自有楼栋 / 门牌 / POI 数据**：同一引擎的 A 类路径直接可用；迪拜 Makani、沙特国家地址接口 |
| 弱标注 | 商户坐标噪声因国家而异（斯洛文尼亚、拉脱维亚明显偏高） | 真实订单 + 签收坐标重新评测、重拟合置信度和放宽规则（标注规范见 [mvp/labeled/GUIDELINE.md](../mvp/labeled/GUIDELINE.md)） |
| 本地小模型收益小、延迟高 | 测试集 −4 到 +4 个百分点（只测了 4 个市场），CPU 上 7–9 秒 / 次 | 默认关闭；批量清洗或有 GPU 时用 `--intl-llm` 开启 |
| 美国 | 按要求不做 | — |

## 10. 复现

```bash
cd mvp && pip install -r requirements.txt
python scripts/fetch_markets.py               # Overture 数据（44 个市场，约 3 GB）
python scripts/fetch_osm_addresses.py         # OSM 门牌 + 道路编号（BBBike / openstreetmap.fr 摘录，约 2.5 GB 下载，处理完删除）
python scripts/build_market_reference.py      # 参考库（3 路并行约 25 分钟）
python scripts/train_market_parsers.py        # 机器学习解析器（每个市场约 30 秒）
python scripts/fit_accept_policy.py           # 按市场校准直接通过的放宽规则（开发集）
python scripts/fit_intl_confidence.py         # 置信度（开发集拟合、测试集检验）
python scripts/evaluate_markets.py --split test --n 1000 --jobs 3  # 测试集 -> reports/markets_eval.md
python scripts/google_parity.py --split test --jobs 4              # 与 Google 对标（测试集）-> reports/google_parity.md
python -m avmvp.server                         # 演示页面 http://127.0.0.1:8080/
pytest -q                                      # 单元测试（多市场用微型夹具，无需下载）
```
