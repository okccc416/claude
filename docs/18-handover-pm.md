# 18 · 交接说明（产品）

> 2026-10-29。研发细节见 [19 · 交接说明（研发）](19-handover-dev.md)，逐国结果见 [Google 实测对照](../mvp/reports/google_real_compare.md)。

## 1. 结论

**和 Google 跑同一批线上查询：Google 做对的 851 条，我们的服务做对 637 条（74.9%）。有官方门址数据的 14 国做对 88.5%，没有门牌数据的 7 国只有 50.0%，差距主要在这里。**

| 国家的数据条件 | Google 做对 | 我们也做对 | 各国：我们做对 / Google 做对 |
|---|---|---|---|
| 有官方门址数据（14 国） | 416 | **368（88.5%）** | 法国 27/28、荷兰 23/24、波兰 43/45、奥地利 24/26、意大利 35/38、巴西 23/25、德国 26/29、新西兰 36/41、比利时 28/32、澳大利亚 19/22、葡萄牙 12/14、西班牙 29/34、墨西哥 21/25、哥伦比亚 22/33 |
| 没有官方门址表（6 国） | 126 | 86（68.3%） | 马来西亚 23/28、菲律宾 20/25、英国 25/32、越南 5/9、泰国 9/19、印尼 4/13 |
| 没有开放门牌数据（7 国） | 198 | **99（50.0%）** | 多米尼加 24/34、巴林 19/33、沙特 16/29、阿联酋 1/2、埃及 16/33、哈萨克斯坦 13/34、科威特 10/33 |
| 只核对 geo，没接参考库（7 国） | 111 | 84（75.7%） | 新加坡 5/5（这次没接新加坡引擎）、土耳其 12/14、阿曼 26/31、秘鲁 27/36、卡塔尔 3/4、乌兹别克斯坦 6/11、南非 5/10 |
| **合计** | **851** | **637（74.9%）** | 只用现有 geo：561（65.9%） |

- **口径**：数据是公司线上评测的 1,000 条查询，Google 做对 854 条。只有 Google 做对的查询有标准答案（库内目标门址坐标），所以只能比"Google 做对的，我们做对多少"。按全部 1,000 条算是 Google 85.4%、我们 63.7%，Google 做错的 146 条记我们全错，偏向 Google。
- **我们的服务** = 现有 geo 的结果 + 我们的核对层，geo 不对时用我们自己的引擎。不带 geo、只用我们自己的引擎是 326 条（38.3%）：引擎只在试点城市和 11 国全国门址库里有数据，这 851 条里 57% 在试点城市以外或没接参考库的国家。
- **差在哪**：我们没做对的 214 条里，177 条正确答案根本不在我们手里（geo 给错或偏了 100–500 米，我们的数据里也没有这个门牌）；只有 37 条是判断没选对，换更强的判断模型最多多救这 37 条（+4.3 个点）。**要追 Google，靠补数据，不靠换算法。**
- **现有 geo 加上我们的核对层，可以先上线**：直接用 geo，有 213 条错地址被采用；加核对层后只剩 13 条（直接通过的 2.6%），geo 的错拦下 94%。
- **悉尼数据完整，效果最好**：客户 421 万条门址底表 96.6% 与官方门址库 G-NAF 吻合，缺的 suburb、邮编能补 97.9%；用底表合成的查询定位对 93.0%，给错还直接通过的只有 0.1%。
- **速度**：单条 P99 50 毫秒，最慢 171 毫秒，满足 300 毫秒的要求。

## 2. 技术链路

```
用户输入 → 去噪（电话、收件人、备注） → 拆字段（规则 + 机器学习，参考数据裁决）
        → 在参考数据里找候选（试点城市地址库；城市以外查全国门址库）
        → 逐字段核对门牌、路名、片区、邮编 → 结论：直接通过 / 请用户确认 / 请用户补全
        → 输出标准地址、补上的字段、置信度（与 Google 地址验证同一接口）
带 geo 结果时：先把 geo 的门址代回原文和参考数据核对，自洽才直接通过；不自洽就用我们自己的结果
```

- 不用大模型、不调外部接口，单机就能跑。
- 接口与 Google Address Validation 相同，可以直接替换。

## 3. 其他国家的拓展

| 项 | 现状 |
|---|---|
| 覆盖 | 50 个市场：新加坡全境，其余 49 国各一个试点城市。试点城市以外：11 国有全国门址库，能到门牌；其余国家只能到城镇 |
| 加一个国家要做什么 | 写配置（邮编格式、门牌写在前还是后、路名缩写），拉开放数据（Overture、OSM、当地政府），自动训练拆字段模型。引擎代码不用改。第二批 5 国（科威特、巴林、埃及、哈萨克斯坦、多米尼加）就是这样加的，线上做对 66 → 82 条 |
| 全国门址库的效果 | 试点城市以外的 227 条线上查询，定位对 60.8% → 87.7% |
| 效果上限由数据决定 | 试点城市内按 Google 公开规则估算（不是实测），38 个 Google 覆盖的市场里 26 个与 Google 持平；没持平的 12 个都缺数据 |
| 要补的数据 | 当地全量门牌：墨西哥、葡萄牙、爱尔兰、马来西亚、波多黎各、印度；中东、东南亚的楼栋 / 门牌（自有或采购）；全国门址库扩到更多国家 |

## 4. 其他方案和说明

**试过、没采用的方案**（每行都是在同一测试集上和本方案比）：

| 方案 | 结果 |
|---|---|
| 整串模糊匹配（常见 geocoder 做法） | 新加坡完全正确 53.9%，本方案 99.9%；给错还直接通过 13.9%，本方案 0 |
| 本地大模型兜底（Qwen3-4B） | 只多 0–4 个点，泰国反而 −4；每条 7–9 秒，不能进实时链路 |
| 开源 libpostal 拆字段 | 只多 0.2 个点，每个进程多占 2 GB 内存 |
| 开源 Pelias（导入同一份澳洲数据） | 定位对 82.7%，本方案 86.0%；它的置信度分不开对错，没法自动通过 |
| 开源 Addok + 法国官方地址库 | 定位对 89.5%，本方案 94.3%；准确率都约 98% 时，自动通过 46.7%，本方案 89.2% |

**下一步**：
1. 上线 geo 核对层：只采用"直接通过"的结果，其余请用户确认。
2. 取悉尼真实查询日志 ≥ 1,000 条（用户输入 + geo 候选 + 签收坐标）。线上如果同时调过 Google，把同批 Google 结果一起取，在同一份标准答案下比 Google、现有 geo、我们三方。悉尼现在只有合成查询和 22 条线上样本。
3. 按第 3 节补数据。
4. 法务确认数据授权：澳洲 G-NAF、巴西、加拿大、墨西哥等地址表是专有许可。
