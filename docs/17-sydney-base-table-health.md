# 17 · 悉尼门址底表体检（对照 G-NAF）与合成评测

> 数据：悉尼门址底表（Data Agent 的地址向量检索库，全量 4,212,740 条，`vector` 列已去掉）。
> 对照：全国门址库里悉尼一带的 G-NAF 门址点（Overture 2026-09-23.1，底表坐标范围外扩 15 公里内共 321.7 万个点）。
> 本文和 `mvp/reports/sydney_base_health.json`、`mvp/reports/base_synth_eval*.md` 只有汇总数字和合成的输入样例，没有底表原始行。

## 1. 结论

1. **底表就是 G-NAF 派生的标准门址表，坐标质量很高。** 96.57% 的门址在 G-NAF 里能找到同路、同门牌的点，坐标在 30 米以内（中位 0.7 米，P90 1.2 米）。算上偏 30–500 米的和只差方位后缀的，97.69% 对得上。
2. **suburb 和邮编可以补齐。** 底表没有这两列；97.86%（412 万条）可以直接从 G-NAF 补上。同一 district 下的同名门址 5.6 万组，补上 suburb 后 68% 直接分开；剩下的大多是下面第 4 条说的重复收录。
3. **门址本身要处理的约 2.4%**，按量排：
   - 附近有这条路、门牌在 G-NAF 找不到：1.66%（7.0 万条）。其中六成是坐标落在同一条路的另一个门牌上（转角、合并地块、改过号），9% 是带字母的门牌（12A）而 G-NAF 只有 12，三成附近没有任何 G-NAF 点（新建或 G-NAF 快照里还没有）。
   - 路名找不到：0.29%（1.2 万条）。2,613 条把路名写成了公路编号（A28 这类），其余多是新开发片区的新路。
   - 只有地块号的临时地址（LOT n + 路名）：0.21%（8,872 条），其中 83% 在 30 米内已经有 G-NAF 正式门牌，可以直接换掉。
   - 方位后缀不一致：0.13%（底表少写或多写了 NORTH / EAST 之类）。
   - 坐标放错地方：0.08%（3,385 条）。同路同门牌在 G-NAF 里，但离底表坐标 500 米以上（中位 9.8 公里）。
4. **重复收录、坐标不一致：1.28 万组、2.7 万行。** 同一 suburb 里同一条门址出现多次、坐标相距 10 米以上（74% 相距 50–200 米，26% 相距 200 米–1 公里）。GU 召回时会出两个候选，建议只留与 G-NAF 吻合的那条。
5. **坐标热点：256 个坐标点各挂了 10 条以上不同的路（9,396 行）**，536 个点挂了 5 条以上（1.5 万行）。这类点多半是缺坐标时填的占位坐标，建议换成 G-NAF 坐标。
6. **覆盖很全。** 底表服务范围内（底表里至少 50 条门址的 793 个 suburb），G-NAF 的 148 万个门址（路名 + 门牌，不分单元）里底表缺 2.4 万个（1.6%）；724 个 suburb 缺口不到 5%。缺得多的是新开发片区（Gilead 缺 43%）和城郊农村（Londonderry、Orchard Hills、Castlereagh 一带缺 17–21%），以及 Gladesville（21%）。
7. **district 列不能当 suburb 用。** 大多数是 LGA（议会）名；Wingecarribee、Hawkesbury 一带写的是 locality，但不少实际在相邻 suburb。`q`（778 行）实际是 Watsons Bay，`派珀角`（1,451 行）是 Point Piper（中文译名），可以直接改。
8. **两类来源差别不大。** 32 位 hex 编号的行吻合率 96.98%，UUID 编号的 95.84%；UUID 行新路更多（路名找不到 0.48% 对 0.18%）。混合大小写的行（5.2%）坐标精度差一些：偏 30–500 米的占 5.05%，全大写的只有 0.77%。

## 2. 方法

每条底表门址拆出单元、楼层、门牌（含区间 38-48）、路名，在 G-NAF 里找"同路名 + 同门牌"的点：

| 步骤 | 做法 |
|---|---|
| 路名比较 | 用引擎的澳洲路名规范化（类型词缩写展开，`CLOS` → `CLOSE`），再去空格比较（POWDER WORKS = POWDERWORKS） |
| 门牌 | 区间门牌整串、首号、尾号都查；底表写单号而 G-NAF 存区间（16-20 含 18）也算 |
| 方位后缀 | 对不上时去掉 NORTH / SOUTH / EAST / WEST 再比，单独记为"后缀不一致" |
| 附近有没有这条路 | 约 1 公里的格子，查周围 3×3 格 |
| LOT 地址 | 看 30 米内同一条路有没有 G-NAF 正式门牌 |
| 覆盖缺口 | 服务范围内每个 suburb 的 G-NAF 门址（路名 + 门牌），看底表里有没有吻合的行 |

脚本：`mvp/scripts/base_table_health.py`。同一个脚本输出逐行补齐结果（编号、分类、距离、suburb、邮编、官方路名和门牌），给底表回填用；全量跑一遍约 30 分钟。

## 4. 建议（按收益排）

1. **补 suburb 和邮编**：用补齐结果直接回填，约 98% 的门址有值。这是 GU 召回和评测都缺的字段，也让同名门址不再歧义。
2. **去重**：同一 suburb 里同一条门址的多条记录（1.28 万组），留与 G-NAF 吻合的那条。
3. **修 district**：`q` → Watsons Bay，`派珀角` → Point Piper；district 只当 LGA 用，suburb 以补上的为准。
4. **换掉 LOT 临时地址**：30 米内已有正式门牌的直接改成正式门牌（83%），其余保留并标记"临时"。
5. **坐标热点和放错的坐标**：挂了很多条路的占位坐标（约 1.5 万行）和偏 500 米以上的（3,385 行）换成 G-NAF 坐标。
6. **路名规范**：公路编号写成路名的换成 G-NAF 路名；方位后缀与 G-NAF 对齐；`CLOS` 这类截断类型词补全（25,245 行）。
7. **补覆盖缺口**：新开发片区和城郊的 2.4 万个 G-NAF 门址底表里没有，可以从 G-NAF 补进来。
8. **门牌找不到的 1.7%**：不急着删。附近没有 G-NAF 点的多是新建，保留；落在同路另一门牌上的，抽样人工看一批再决定。

## 5. 用底表合成的查询评测

底表没有用户输入，不能直接当评测对用。这里用补齐后的底表按用户常见写法合成查询，看引擎在客户真实门址分布上的表现。**这是合成数据，不是真实用户输入**，结论要用真实查询日志再核对。

做法（`mvp/scripts/base_table_synth_eval.py`）：只取与 G-NAF 吻合的门址；按编号哈希固定分成开发 / 测试两半，开发集用来改进，测试集只在最后跑一次；每条门址渲染成一种写法：

## 6. 引擎上的改动

体检和合成评测暴露了几处问题，改动如下：

1. **澳新官方路类型缩写**：CIR、ESPL、DVWY、GLN、VW 等 Australia Post / G-NAF 写法，以及门址库里常见的截断写法 CLOS、GLAD，补进 AU、NZ 两个市场（只收不会和普通词撞的写法）。
2. **全国门址库交叉核对**：悉尼试点框（参考库）以外的 Penrith、Campbelltown、Blacktown 西北一带，范围守卫判成了"框内"，试点参考库只收到框内的一截路，常配到框内甚至墨尔本的同名路。现在试点结论站不住（只到片区、带邮编 / 片区对不上、路名推断或纠正、门牌查不到、多个候选，或者写了 suburb 而试点结论没有印证）时，全国门址库能确证"路名一致、门牌一致、邮编或 suburb 印证、全国只有这一处"，就以全国门址库为准。原文写的邮编和全国库那一处不同、只靠城市名印证（Lisboa、Warszawa）时不换。
3. **只写门址行的地址**：没写 suburb、邮编、城市名，试点参考库里只有一处就直接通过了；现在试点都市圈里（试点框外扩约 50 公里）还有别的同名同号时改成请用户确认。
4. **全国库的查法**：城镇名没用逗号隔开、夹在路名后面时（`25 hall street pitt town 2756`），按每个候选自己的城镇把它从原文里拿掉再比路名，免得以城镇命名的路（Pitt Street）对上；邮编和城镇都对上的候选加分；段尾的州缩写（NSW）去掉；路类型缩写按国家展开；前面只有单元号的写法（`U56/1 Limestone Rd`）能找到路名；路名和城镇同名（`Thirlmere Way, Thirlmere`）时城镇照样算印证；拉丁文路名不再因为前缀相同就对上（PARK 不是 PARKSIDE）。
5. **噪声**：派送备注直接连着地址（`leave at door 166 Cox St`）能切掉；收件人名字切到单元词为止（`attn: j. smith apt 2 12-20 …` 的 apt 2 是单元）。
6. **解析**：机器学习解析器把 `13/7-9` 拆成单元 13、门牌 7-9（原来把单元号当门牌）。

## 7. 性能（目标：单条 ≤ 300 毫秒）

体检时发现全国门址库的查询很慢：悉尼合成查询改动前就有 P95 约 500 毫秒、P99 约 700 毫秒（试点框外的地址都要查全国库）。改动后同一台机器、单进程、引擎预热之后：

| 测试集 | 条数 | P50 | P95 | P99 | 最慢一条 | 超过 300 毫秒 |
|---|---:|---:|---:|---:|---:|---:|
| 悉尼合成查询（开发 + 测试） | 4,200 | 6.7 ms | 28.8 ms | 50.1 ms | 133 ms | 0 |
| AU 开发集（真实商户 + 合成） | 1,600 | 4.4 ms | 23.6 ms | 45.0 ms | 105 ms | 0 |
| DE / ES / NL | 各 1,600 | 2.4–3.0 ms | 12–22 ms | 27–66 ms | 99–171 ms | 0 |
| CO / BE / PT / PL / AT / NZ | 各 1,600 | 2.1–4.8 ms | 10–42 ms | 17–97 ms | 32–154 ms | 0 |

做了这几件事（结论基本不变：10 个市场 1.6 万条里 4 条结论变了，1 条变好、1 条变差，另 2 条只是在两种 FIX 之间变）：

1. **全国门址库补"门牌 + 邮编"索引**。原来按邮编查同号门牌要扫全国同号的门牌（澳洲门牌 12 有几十万个），单条几百毫秒。已有的库用 `python scripts/fetch_national.py --markets AU --add-indexes` 补建（每国 10–70 秒）。
2. **路名比对的缓存**：原文这一侧、官方路名这一侧、转写骨架按字符串缓存，同一条原文和几百个候选比时不重复计算。
3. **全国库少查**：先查所写邮编 / 城镇里的同号门牌，邮编印证（或路名完全对上且城镇印证）、不歧义时，不再按路名前缀全国召回；大城市按城镇召回超过 3,000 条时加路名前缀条件；写了邮编 / 城镇时，全国前缀召回超过 5,000 条就不查（只为救"邮编写错"）；候选路超过 1,500 条时先按核心词预筛。
4. **加载时预热**（`Engine.warm()`，服务加载引擎时自动调用）：先建好第一次用到才建的索引；把参考库和全国库文件读进系统页缓存（之后的查询不读盘）；合成几条地址跑一遍；把几百万个常驻对象冻结出 Python 的垃圾回收（否则偶尔停顿几百毫秒）。代价是加载慢一些：澳洲约 7 秒；全国库在冷盘上时要先读一遍文件（德国 3.3 GB 约 100 秒，已在页缓存里 3 秒）。全国库靠系统页缓存、不占进程内存；10 个国家一共 18 GB，内存不够时只开用到的国家。设 `AV_WARM_DB=0` 可关掉文件预读。

## 8. 对后续评测的影响

- 底表坐标和 G-NAF 基本一致，评测时"判对"可以直接用坐标距离（30 米内算门牌级正确）。
- 第 15 篇第 4 节的对比测试还是要真实查询日志（用户输入 + GU 结果 + 签收坐标或人工标注）。合成评测说明了引擎在客户门址分布上的上限，用户真实写法的分布要靠日志校准。
