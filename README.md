# Address Validation 能力建设方案（对标 Google Address Validation API 与 Loqate）

> 面向：新加坡地图能力供应商 · 产品经理 / 能力建设负责人
> 前提：公司已有 Geo（地理编码 / 检索）能力，计划新建 **地址校验（Address Validation, AV）** 能力，对标 Google Address Validation API 与 Loqate（GBG）的验真 + 补齐能力。

---

## 一句话定义

**Geocoding 回答"这个地址在哪"，Address Validation 回答"这个地址对不对、全不全、能不能送达，以及哪里不对、该怎么改"。**

Google AV 的核心产出不是坐标，而是一个**可执行的结论**（`ACCEPT / CONFIRM / FIX / CONFIRM_ADD_SUBPREMISES`）+ **逐组件的可信度判断** + **标准化后的地址**。

---

## TL;DR：先记住这 7 件事

1. **AV ≠ 更好的 Geocoding。** Geocoding 的目标是"总能给你一个最可能的点"；AV 的目标是"敢说不"——要能指出门牌不存在、邮编和街道冲突、缺单元号。这要求你有**"存在性"级别的参考数据**，而不只是路网和插值。
2. **数据是护城河，算法是门槛。** 解析、匹配、打分这些算法 3–6 个月能做到可用；但楼栋 / 门牌 / 单元级的权威参考库、以及"某个区域的数据有多全"的认知，才决定你能不能比 Google 准。
3. **Google 在东南亚有明显空白，但这个空白正在被 Loqate 填补。** Google AV 在东南亚仅覆盖新加坡、马来西亚（GA），印尼、泰国、越南、菲律宾不在覆盖范围；美国以外基本不能判断单元号缺失 / 错误；无原生批量接口；缓存 / 存储条款严格。而 Loqate 自 2024 年起接入 GrabMaps 的东南亚数据（2025 年扩展到新加坡、印尼、泰国、菲律宾、越南）——**在 Google 没覆盖的市场，真正的对手很可能是 Loqate。**
4. **先定"评测体系"，再写第一行代码。** 建一个按国家 × 错误类型分层的 Golden Set，同时跑 Google AV、你们现有 Geocoder，拿到 baseline 再立项，所有后续迭代都靠它说话。
5. **首发建议：新加坡先行（数据好、本土市场、能打到单元级），再选一个"Google 没覆盖但你有数据"的市场做差异化（越南 / 印尼优先评估）。**
6. **两个对标对象代表两种路线：** Google 是"地图公司做地址"（结论导向、开发者友好）；Loqate 是"数据质量公司做地址"（补齐 + 验真两件套、过程编码、原生批量、私有化、OEM 进 MDM 平台）。**我们作为本地地图厂商，应该取两家之长**：Google 式的直接结论 + Loqate 式的补齐下钻、批量和私有化 + 我们独有的入口点和本地深度。
7. **最大的非技术风险是数据授权和竞品服务条款。** 邮政数据的商用授权、OSM 的 ODbL 共享义务、以及"不能用 Google 的输出来训练 / 改进竞品"（Loqate 同理）——立项前必须拉上法务。

## 可运行的服务：新加坡 + 11 个市场

[`mvp/`](mvp/README.md) 是一个已经实现、可在本地运行的地址校验服务（Python，带演示页面和 HTTP 接口，按 `regionCode` 分发）：新加坡用专用引擎；**澳洲、德国、法国、荷兰、阿联酋、沙特、马来西亚、印尼、泰国、越南、菲律宾**用多市场引擎（各 1–2 个试点城市，见 [13 文档](docs/13-multi-market-product.md)）。

**多市场**（每市场 1,000 条真实商户自填地址，商户本身不在参考库里；规则 + 机器学习混合解析）：

| 类别 | 市场 | 找对 | 其中直接通过 | 偏差 >1 公里的静默错误 |
|---|---|---|---|---|
| A：有开放官方地址表，逐门牌验真 | 德国 / 法国 / 荷兰 / 澳洲 | 95.1% / 92.7% / 87.7% / 78.6% | 93.9% / 90.3% / 83.1% / 74.3% | 0.1–1.5% |
| B：中东，验到楼宇 / 道路 | 阿联酋 / 沙特 | 32.7% / 37.1% | 1.9% / 2.8% | 0.5% |
| C：东南亚，验到楼宇 / 道路 | 马来西亚 / 越南 / 菲律宾 / 印尼 / 泰国 | 72.7% / 67.5% / 61.7% / 61.6% / 60.3% | 11.0–33.1% | 0.6–1.6% |

每个结论带校准过的置信度（测试集上校准误差 1.3%，AUROC 0.867），客户可以用 `confidenceThreshold` 自己设自动通过的门槛。

规则 vs AI：两种解析都出候选、由参考数据裁决的混合方案在每个市场都最好或并列最好；纯机器学习在合成地址上最好、在真实地址上最差。**中东和东南亚的瓶颈是参考数据（门牌、楼名），不是解析**：接入自有楼栋 / 门牌数据后，同一引擎可以逐门牌验真。

**新加坡**：在 13.3 万个真实地址构成的参考库上，用从未参与开发迭代的测试样本评测。

标准变形（4,000 条）：

| 方案 | 完全正确率 | 误收率 | 误拒率 | 静默错误率 | 单条延迟 |
|---|---|---|---|---|---|
| **MVP 方案** | **99.9%** | 0.0% | 0.1% | 0.0% | P50 约 1ms |
| 直接复用地理编码式的整串模糊匹配 | 53.9% | 7.0% | 28.3% | 13.9% | — |
| 只查邮编 | 57.6% | 0.0% | 35.7% | 12.8% | — |

真实客户输入风格（1,800 条，混着电话、收件人、配送备注、AMK 等本地缩写、粘连和错拼）：地址识别率 **98.8%**，**87.2%** 可直接通过（未做噪声处理的最初版本只有 13.8%），电话 / 收件人 / 备注被单独拆出返回，静默错误 0%。

在按真实订单分布模拟的 10,000 单标注数据上（[10 文档](docs/10-labeled-data.md)，含新楼盘、马来西亚地址、App 自动补全等开放世界情况）：结论合理率 96.1%，误拒 0.3%，缺单元号检出 74.0%（按真实写法升级前分别为 85.6%、1.0%、22.5%），静默错误 0.45%，主要来自"文字自洽但指向别的真实地址"的输入。

按调研比例构造的测试集（[11 文档](docs/11-research-testset.md)：标准地址取自 2026 年官方地址表，噪声比例来自文献和 10.6 万条真实人写地址的实测）与 8,000 条真实人写地址上：可确定地址找对 99.5% / 99.2%，静默错误 0.02% / 0；真实人写地址直接通过 85.9%（升级前 76.9%）。**最大的问题是参考库过时**：9.6% 的组屋楼栋不在 2017 参考库里，换成 2026 年数据（许可相同）找对率从 86.7% 升到 93.8%，服务现在默认使用 2026 年数据。

消融实验表明每个核心模块都不可省略（去掉任一模块下降 4.9–12.7 个百分点）。**最大的风险不在算法，而在参考数据的时效**：模拟新楼盘未进库时，96% 的新地址会被误拒。详见 [07 文档](docs/07-mvp-technical-validation.md)。

```bash
cd mvp && pip install -r requirements.txt
python scripts/fetch_data.py && python -m avmvp.server   # 新加坡；打开 http://127.0.0.1:8080/
python scripts/fetch_markets.py && python scripts/build_market_reference.py && python scripts/train_market_parsers.py  # 其余 11 个市场
```

## 立项前，需要你们内部先回答的 9 个问题

这些问题的答案会直接改变方案的优先级，建议在 Discovery 阶段逐一明确：

1. **谁买单？** 目标客户是电商结账、物流快递、外卖 / 即时配送、金融 KYC，还是企业主数据清洗？（不同客户对"误收"和"误拒"的容忍度完全不同）
2. **在哪卖？** 首批目标国家是哪几个？现有 Geo 能力在哪些国家最强？
3. **我们手里有什么数据？** 楼栋 / 门牌点？单元级？邮编库？POI？有没有来自客户或合作方的**配送签收 GPS**、**用户搜索 → 最终选点**日志？
4. **现有 Geo 的地址解析器（parser）是什么水平？** 能否输出结构化组件？有没有 N-best 候选和置信度？
5. **是否要兼容 Google 的 API 结构**，以降低客户迁移成本？
6. **定价定位**：比 Google 便宜多少？还是同价但更准 / 覆盖更广？
7. **部署形态**：只做公有云 API，还是需要私有化 / 数据驻留（政府、金融客户常见）？
8. **数据采购预算**：邮政数据、商业地址库的授权费用有没有预算？
9. **卖服务还是卖数据？** 自营地址校验 API，还是把本地数据授权给 Loqate 这类全球厂商，或两者都做？（Loqate 已从 GrabMaps 采购东南亚数据，说明这条路存在；两者会有渠道冲突，见 [06 文档](docs/06-loqate-teardown.md)）

## 这周就可以开始做的 5 件事

1. **约 5–10 个现有客户访谈**：他们现在怎么处理坏地址？每年因地址问题损失多少（退件、改派、客服工单）？是否在用 / 评估 Google AV？
2. **亲手试用两个竞品**：注册 Google Maps Platform 和 Loqate（有免费试用 credit），用同一批 20 个新加坡 / 马来西亚地址 + 20 个印尼 / 越南地址分别调用，对照 [01](docs/01-google-av-teardown.md) 和 [06](docs/06-loqate-teardown.md) 文档理解两家的响应结构，重点看 Loqate 在 Google 未覆盖国家的表现；顺便体验 Loqate Capture 的"邮编 → 地址"下钻交互。*（注意服务条款，见 04 文档）*
3. **盘点内部数据资产**：按 [03 文档](docs/03-data-strategy-sea.md) 的 L0–L7 数据分层列清单，标注每个国家每一层的"有 / 无 / 质量"。
4. **拉一个 500 条的新加坡 Golden Set v0**：按 [04 文档](docs/04-evaluation-framework.md) 的 9 类错误分层，先用现有 Geocoder 跑一遍，看看离"能做判定"差多远。
5. **拉上法务**：邮政数据授权、OSM ODbL、Google 与 Loqate 服务条款中关于对比测试和使用输出的限制。
