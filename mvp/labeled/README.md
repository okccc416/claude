# 模拟订单标注数据 v1（新加坡）

> **这是模拟数据，不是真实订单。** 在还没有真实订单时，按"真实订单大概会长什么样"生成的 10,000 单带标注的地址数据，用来统计置信度、评测校验器，并作为以后标注真实订单的格式样板。
> 标注口径见 [GUIDELINE.md](GUIDELINE.md)；评测结果见 [docs/10](../../docs/10-labeled-data.md) 与 [reports/labeled_eval_report.md](../reports/labeled_eval_report.md)。

| 项目 | 内容 |
|---|---|
| 文件 | `orders_sg_v1.csv`（UTF-8，10,000 行，约 3.2 MB） |
| 切分 | 训练 6,000 单（只用于统计置信度）/ 测试 4,000 单（只用于评测）；**按真实地址切分**，同一地址不会同时出现在两边 |
| 生成 | `python scripts/make_labeled_orders.py`（固定随机种子 20261015，重跑结果逐字节一致） |
| 评测 | `python scripts/evaluate_labeled.py` |
| 参考库 | OneMap 邮编导出（2017 年起），与校验器使用的是同一份 |

> 本目录还有第二份数据 **`testset_sg_research_v1.csv`**（5,000 条，全部为测试数据）：标准地址取自 2026 年官方地址表，噪声种类和比例来自文献与 10.6 万条真实人写地址的实测，包含真实的新地址。见第 8 节与 [docs/11](../../docs/11-research-testset.md)。

## 1. 每一行是什么

一行 = 一个订单：客户在某个渠道提交的地址文字 + 标准答案。

| 字段 | 含义 |
|---|---|
| `order_id`、`split`、`channel` | 订单号、训练 / 测试、下单渠道 |
| `address_line1`、`address_line2`、`postal_field` | 客户在表单里分别填的内容（聊天渠道整段放在 `address_line1`） |
| `input` | 送进校验器的文字（按渠道把各字段拼起来，和真实系统的做法一致） |
| `truth_eid`、`truth_blk`、`truth_street`、`truth_postal`、`truth_building`、`truth_unit` | **真实投递地址**（相当于签收结果）；`truth_eid` 是参考库编号，参考库里没有的地址留空 |
| `property_type`、`unit_required` | 物业类型（组屋 / 公寓 / 写字楼 / 有地住宅）、是否需要单元号 |
| `text_resolution` | **只看文字**能判断到什么程度：可确定 / 有歧义 / 矛盾 / 误导 / 参考库没有 / 非新加坡 / 没有地址 |
| `gold_action`、`acceptable_actions` | 期望结论（BALANCED 档）与不算错的结论 |
| `error_tags`、`field_states`、`label_note` | 输入里有哪些问题、逐字段状态、判断依据 |

字段定义和判断规则的完整说明见 [GUIDELINE.md](GUIDELINE.md)。

## 2. 怎么造的

### 2.1 按渠道模拟"客户怎么填"

| 渠道 | 占比 | 怎么填 | 主要问题 |
|---|---|---|---|
| 网页结账表单 `web_form` | 41% | 地址行 1 / 地址行 2 / 邮编分开填 | 漏填单元号（13%）、缩写、重复粘贴 |
| App `mobile_app` | 25% | 先填邮编，自动带出楼栋和道路，再手填单元号 | 漏填单元号（6%）；**邮编打错且恰好是另一个真实邮编时，自动带出一整套"自洽但错误"的地址** |
| 聊天下单 `chat` | 16% | WhatsApp / Telegram 自由文本，夹着姓名、电话、备注 | 不写邮编（19%）、漏单元号（17%）、本地缩写、错拼、中文地址 |
| 电商平台导出 `marketplace` | 10% | 全大写、字段拼接、`SINGAPORE, SINGAPORE` 重复 | 字段长度截断、电话混进地址 |
| 企业批量上传 `b2b_upload` | 9% | 商家 Excel，写字楼为主 | 只写楼宇名 + 单元号、Excel 吞掉邮编前导 0、公司名和联系人混进地址 |

各渠道的错误比例写在 `scripts/make_labeled_orders.py` 的 `PROFILES` 里，都是**经验假设**（见第 5 节）。

### 2.2 按下单人群抽地址

- 个人订单：组屋 66%、公寓 16%、写字楼 10%（送到公司）、有地住宅 8%。依据是新加坡约八成居民住在组屋；企业上传以写字楼为主（80%）。
- 物业类型判断：组屋用**邮编规则**（组屋邮编 = 2 位邮区 + 字母后缀编码 + 3 位楼号，如 Blk 655C → 823655），比较准；公寓 / 写字楼靠楼宇名关键词，是启发式判断。

### 2.3 错误注入（独立实现）

错拼模型（键盘相邻键、漏字母、双写、对调、元音混淆、空格错位，以及 Sarangoon、Pungol 这类本地常见错拼）、缩写表（包含校验器词典里没有的 `Cent`、`S'goon`、`W'lands`、`E Coast` 等）、单元号写法、渠道格式，全部重新编写，**没有复用校验器或旧测试集的任何词典**。

还包含旧测试集没有的开放世界情况：

| 情况 | 占比 | 说明 |
|---|---|---|
| 参考库里没有的新地址 | 1.9% | 新组屋楼号（如已有 322，新增 322C）、新片区道路、新公寓；**门牌、邮编、公寓名均为虚构** |
| 没有地址 | 0.8% | `self collect`、`same as previous order`、只写区域名 |
| 马来西亚地址 | 0.6% | 柔佛州地址；其中 `Jalan Setia` 这类路名新加坡也有同名道路 |
| 中文地址 | 0.1% | `宏茂桥6道123座` |

### 2.4 标注

- **真实地址**：生成时就知道（相当于完美的签收数据）。
- **只看文字能判断到什么程度**：由独立的标注规则给出，模拟"拿着参考库逐字段查询的标注员"。它只看客户写了哪些字段、写成了什么，不调用校验器。规则见 [GUIDELINE.md 第 2 节](GUIDELINE.md#2-text_resolution只看文字能判断到什么程度)。
- **期望结论**：按 [GUIDELINE.md 第 3 节](GUIDELINE.md#3-gold_action期望的校验结论balanced-档) 的对照表给出。

## 4. 质量检查

**自动检查**（`tests/test_labeled.py`）：期望结论一定在可接受集合里；有真实地址 ⇔ 不是"参考库没有 / 非新加坡 / 没有地址"；训练和测试部分没有共同的真实地址；生成结果可复现；标注规则在夹具数据上的典型情况（错拼、邮编打错撞上真实邮编、字母后缀漏写、共用邮编、重复记录）判断正确。

**人工抽检**：我按标注规范逐条阅读了约 200 条（分三轮：试生成 2,000 单、第一版 10,000 单、最终版；最终版按订单号系统抽样 50 条 + 各稀有类别 30 条）。发现并修正了 8 个问题，最终版抽检未再发现标签错误：

| # | 问题 | 处理 |
|---|---|---|
| 1 | 楼栋号漏写字母后缀（268A 写成 268）比例设得过高（20–35%） | 调为 3–12% |
| 2 | App 渠道里客户填了别的地址的邮编时，也会自动带出那个地址，原来没有模拟 | 与"邮编打错"同样处理 |
| 3 | 写字楼 / 公寓楼层均匀分布到 40 层，低矮楼宇里出现 #36-01 | 改为偏低楼层分布 |
| 4 | 工地办公室（`TEMPORARY SITE OFFICE`）等被当成收货楼宇 | 排除这类楼宇名 |
| 5 | 电商平台导出里附加的电话号码少一位 | 修正格式 |
| 6 | 地址完整时附加的楼宇名拼错，被要求必须 CONFIRM | 改为"轻微"，直接通过也不算错 |
| 7 | 只写楼宇名并去掉邮编时，`field_states` 仍写 `postal=ok` | 修正状态并加标签 `POSTAL_MISSING` |
| 8 | 参考库同一地址有两条记录（`SAINT` / `ST.`），完整干净的地址被标成"有歧义" | 按"楼栋 + 道路 + 邮编"判断是否同一地址（标注与评测都改） |

抽检是一个人完成的，不是双人独立标注。真实订单请按 [GUIDELINE.md 第 5 节](GUIDELINE.md#5-真实订单怎么标上线前要做的事) 做双人标注并计算一致率。

## 5. 与真实订单的差异（使用前必读）

1. **比例是假设。** 渠道占比、各类错误率、物业类型比例来自经验判断，不是统计。所以总体数字（例如静默错误率 0.33%）只能当量级参考。评测报告按场景、渠道、错误标签分组列出，拿到真实比例后可以按分组重新加权。
2. **错误类型是"想得到的"。** 真实订单里一定有这里没模拟到的写法，例如多地址、地址写在备注里、拼音地址、转运仓地址。
3. **新地址是虚构的。** 本环境无法访问 data.gov.sg / OneMap，拿不到 2017 年之后的真实新地址，所以新组屋楼号、新片区道路、新公寓都是按命名习惯模拟的，不保证真实存在。
4. **物业类型和楼宇名来自启发式判断和 OneMap 原始数据。** 公寓 / 写字楼的判断会有错（例如把有地住宅小区判成公寓）；OneMap 的"楼宇名"常是楼内商户（如托儿所），不一定是客户会写的楼名。
5. **单元号是随机生成的**，不保证这栋楼真有这一层、这一户。
6. **标注规则由同一个作者编写。** 标注规则不调用校验器，但和校验器出自同一人之手，可能有共同的假设（例如"多数字段一致即可确定"与校验器的证据优先级思路相近）。用真实订单 + 独立标注员复核，才能排除这种偏差。
7. **"真实地址"是按构造得知的**，相当于 100% 准确的签收数据；真实世界的签收数据本身也会有错。

## 6. 换成真实订单

真实订单按 [GUIDELINE.md](GUIDELINE.md) 标注成**同样的列**，放到本目录（例如 `orders_sg_real_v1.csv`），然后：

```bash
python scripts/evaluate_labeled.py --orders labeled/orders_sg_real_v1.csv
```

即可得到同样的评测报告，并在 `models/confidence_sg_orders.json` 生成基于真实订单的置信度模型。模拟数据和真实数据也可以合并使用，但评测指标应只看真实订单。

## 8. 第二份：按调研比例构造的测试集 `testset_sg_research_v1.csv`

| 项目 | 内容 |
|---|---|
| 条数 | 5,000（`split` 全部为 `test`，用于评测，不用于统计置信度） |
| 标准地址 | 2026 年官方地址表（OneMap 地址经 OpenAddresses / Overture Maps 发布，13.5 万个地址），不是校验器用的 2017 参考库 |
| 噪声比例 | 每一种都有出处：**实测**（10.6 万条新加坡商户自填地址与官方地址比对，见 `reports/noise_stats.md`）、**文献**（Baymard、Damerau、Verhoeff、新加坡统计局）、**假设**（没有数据的项，单独标出）。完整对照表见 [docs/11 第 3 节](../../docs/11-research-testset.md#3-测试集怎么造make_research_testsetpy) |
| 新地址 | 7.4% 的条目在 2026 年表里有、2017 参考库里没有（**真实新地址**，如 `228B Tengah Drive`），标为 `NOT_IN_REFERENCE` 并带标签 `NEW_ADDRESS_2026` |
| 字段 | 与 `orders_sg_v1.csv` 完全相同；`channel` 统一为 `research_mix`；`truth_eid` 为 2017 参考库编号（新地址留空，真实地址见 `truth_*` 列） |
| 新增标签 | `NUMBER_AFTER_STREET`（门牌写在道路后面，如 `Hougang Ave 2, Block 706`）、`BUILDING_PREFIX`（楼宇名写在地址前面）、`CJK_MIXED`（如 `238号`）、`NEW_ADDRESS_2026` |
| 生成 | `python scripts/fetch_overture.py && python scripts/make_research_testset.py`（随机种子 20261101） |

与第一份的区别：第一份按渠道模拟，比例是经验假设，新地址是虚构的；这一份按字段独立注入，比例有出处，新地址是真实的，但没有模拟 App 自动补全。两份发现的问题一致，可以互相印证。

**许可**：2026 年地址表同为 Singapore Open Data Licence（署名 Singapore Land Authority，见 OpenAddresses 的 `sources/sg/countrywide.json`）。
